## 2. 만든 화면

### 2-1. 구술 목록 (`/`)

기획 문서 IA의 "구술 목록(메인 피드)"에 해당. 처음엔 카드형으로 만들었다가, "카드라고 표현했다고 카드 모양을 의미한 건 아니다"라는 피드백을 받고 **SLV LAB + Women Writing Architecture 참고 스타일**로 전면 재설계했습니다.

- 테두리·그림자 없는 플랫 리스트. zebra 배경으로만 항목 구분
- 날짜가 항상 같은 위치에 고정폭 컬럼으로 정렬 (EDTF 값 기반, `formatEdtfToKorean`)
- 색상 규칙(기획 문서 7-2) 그대로: 파란 태그=인물·장소, 회색 태그=키워드, 형광초록·이탤릭=면담자, 회색·대괄호·이탤릭=지문
- 검색(본문/인물/장소), 키워드 필터, 연도 오름차순/내림차순 정렬 — 모두 실제 동작
- 이견(discrepancy) 발생 행은 옅은 붉은 배경 + "🔍 이견 발견" 표시
- **원문 각주 표시** — "📝 원문 각주" 배지(호버 시 내용). 이견과는 다른 개념(4-2 참고)
- **인물·장소 태그 대신 출처 링크** — narrator_id/interviewer_id 같은 내부 참조 키를 그대로 노출하던 걸 걷어내고, 키워드 태그 아래에 실제 출처(원본 구술 아카이브) 링크 또는 제목을 표시 (4-3 참고)
- "관련자료 N" 펼치면 실제 외부 링크(`target="_blank"`)로 연결되고, 호버 시 유형별 색상 placeholder 썸네일 + 설명이 뜨는 미리보기 팝업 (아래쪽으로 열림 — 처음엔 위로 열려서 본문을 가리는 문제가 있어 수정함)
- 다른 화면에서 `/?focus=<segmentId>`로 들어오면 해당 행까지 스크롤 + 노란색 강조 (연표 화면과의 연결고리)

**주요 파일**: `src/app/page.tsx`, `src/components/SegmentListClient.tsx`, `src/components/SegmentRow.tsx`, `src/components/Tag.tsx`

### 2-2. 연표 (`/timeline`)

가장 많이 반복 설계한 화면. 초기 버전(WWA 표 구조 차용, 4컬럼: 날짜/키워드/제목/내용)에서 한 차례 더 크게 갈아엎었습니다.

**표 구조 (5컬럼으로 재배치)**
- 컬럼 순서: **사료 / 날짜 / 사건명(하단 키워드) / 내용(하단 출처) / 구술** — 사료·구술 컬럼은 다른 컬럼보다 넓게 잡음
- 사료 컬럼: 유형별(사진/신문/문서/논문/지도) 아이콘·색이 다른 placeholder 썸네일, 실제 자료면 클릭 시 원본으로. 유형별 높이도 다르게 줘서(사진>지도>구술>신문·문서·논문) 획일적 그리드 대신 콜라주에 가깝게
- 구술 컬럼: 발췌 길이에 따라 폰트 크기가 반응 — 45자 이하 짧고 임팩트 있는 인용은 크게(17px), 긴 인용은 작게(13px)
- 날짜 정렬 토글, 키워드 필터(제안형 버튼) + 자유 검색어(사건명·내용·장소·키워드·출처 전체 대상)
- 장소 태그는 좌표를 가진 `PlaceRef`로 만들어서 클릭하면 **OpenStreetMap**으로 새 탭 연결 (`src/lib/geo.ts`)
- 도메인은 데이터 범위가 아니라 **1900–2026 고정** — 눈금선 10년 단위, 라벨은 20년 단위(안 겹치게)
- **개인 컬렉션 + CSV 내보내기** — WWA의 "Create Personal Collections and generate PDF readers"를 참고. 사건 옆 ☆ 버튼으로 담고, 화면 하단 바에서 이름 지정 후 CSV 다운로드(`src/lib/csv.ts`). 브라우저 세션 내 임시 상태(새로고침하면 초기화, DB 없음)

**연표 눈금 (상단 고정 바)** — `src/components/TimelineRuler.tsx`
- 스크롤하면 라벨이 있는 132px 눈금이 24px **바코드**로 압축되어 화면 끝까지 따라옴 (`sticky` + 음수 `top` 트릭)
- **관련도 3단계 색이 검색 상태에 따라 바뀜** — 검색어가 없으면 "구술과 직접 교차(주황)/태그 겹치는 간접 연관(파랑)/무관(회색)", 검색어가 있으면 "제목·키워드·장소에 매칭(주황)/내용·출처에서만 매칭(파랑)/무관(회색)"으로 전환 (`relevanceOf()`). 색상 자체도 호박·회색 계열에서 **주황·파랑·회색**으로 전면 교체(요청 반영)

**표시 밀도(SCALE) 3단계**
- **전체**: 사료·구술 컬럼까지 다
- **내용만**: 날짜·사건명·내용만 (사료·구술 컬럼 숨김)
- **제목만**: 날짜+제목만 — 100년 전체를 한 화면에서 훑어보는 인덱스 뷰

이전 버전에 있던 "교차 블록"(행 아래 `↳`로 꺾여 붙는 인용)과 `PhotoInterlude` 개념은 5컬럼 레이아웃으로 흡수되며 사라졌습니다 — 이제 사료·구술이 각자의 독립된 컬럼이라 별도 삽입 블록이 필요 없어졌습니다.

**주요 파일**: `src/app/timeline/page.tsx`, `src/components/TimelineExperience.tsx`, `src/components/TimelineRuler.tsx`, `src/lib/geo.ts`, `src/lib/quotes.ts`, `src/lib/csv.ts`

## 3. 실데이터 연동 현황 (이번 세션에서 새로 생긴 큰 축)

기획 문서·이전 progress.md 어디에도 없던 작업입니다. 목업 데이터를 실데이터로 바꾸는 작업을 시작했고, 현재 `src/lib/real-data.ts` 하나에 전부 모여 있습니다.

### 3-1. 연동에 성공한 것

- **구글 시트(fragments_index) — chronicle · oral segments 탭**: 사용자가 실제로 만들고 있는 라디오/방송사 구술 아카이브 원본. chronicle 25건, oral segments 26건을 그대로 옮김. 시트의 `sources_authority`(출처 제목·링크), `persons_authority`(구술자 이름·출생연도)도 함께 반영해서, 화면에 `P001` 같은 내부 ID 대신 "김청기(1941)"처럼 사람이 읽을 수 있는 형태로 표시되게 함
- **국가기록원 OpenAPI(`searcharc`, data.go.kr)**: 사건 키워드로 검색해 사건 11건에 실제 기록물(사진·문서) 링크를 연결(`src/lib/national-archives.ts`). 인증키는 `.env.local`(커밋 안 됨). 신뢰할 매칭이 없는 나머지는 억지로 붙이지 않고 그대로 미연결로 둠(기획 원칙 "확인 안 된 건 확인 안 된 대로" 유지)
- **국사편찬위원회 "오늘의역사(연표)" 원문파일(data.go.kr, 사용자가 `data/raw/th.xml`로 직접 업로드)**: 전체 15,579건 중 라디오·방송 키워드로 걸러낸 100건을 처리 — 95건은 새 사건(E026~E120)으로 추가, 5건은 기존 사건과 겹쳐서 날짜·내용을 보정하는 데 씀. 그 중 **E016(호출부호 HL 배정)은 기존 자료(9월 3일)와 이 자료(10월 2일)가 서로 다른 날짜를 기록한 이견 사례**라 판단하지 않고 두 값을 그대로 summary에 남김(6-4 원칙)

### 3-2. 확인했지만 연동 안 한(또는 아직 진행 중인) 것

- **한국민족문화대백과사전 OpenAPI(encykorea.aks.ac.kr)**: 인증키 필수 확인, 연구 목적 강조한 신청서 문구 작성 완료. 사용자가 신청 진행 중 — 키 발급 전이라 실제 연동은 아직
- **현대한국구술자료관(mkoha.aks.ac.kr)**: 로그인 없이 검색·상세열람 가능한 걸 확인(JS 함수 `goTotalSearch`/`goView` 직접 호출로 자동화 가능). "라디오"로 검색해 25건 중 2건(박돈서·문영일, 둘 다 청실홍실 라디오 드라마 언급)을 확인해서 persons_authority·sources_authority·oral segments에 붙여넣을 수 있는 표를 사용자에게 전달함 — **사용자가 시트에 붙여넣기를 아직 안 한 상태**로 다음 세션에 이어서 확인 필요. 나머지 23건은 미착수
- **한국학중앙연구원 한국학 디지털아카이브 음성자료 목록(data.go.kr, `15070383`)**: 사용자가 이번에 제시한 신규 후보 3건 중 하나. **완전 자동화 가능함을 실제로 검증함** — 로그인·인증키 전혀 불필요. 2단계 요청(① `POST /tcs/dss/selectFileDataDownload.do`로 `atchFileId` 획득 → ② `GET /cmm/cmm/fileDownload.do?atchFileId=...`)으로 zip을 받으면 안에 CSV 3개: 한국구비문학대계(22,837행, 서명/구연자/채록지/유형), 한국민요대관(13,746행, 노래명/구연자/조사지), 한국방언자료(2,872행, 테잎명/채록자/구술자). curl로 쿠키 없이 바로 성공 확인. 단, **메타데이터 목록일 뿐 실제 음성 파일이나 녹취 전문으로 가는 링크는 없음** — 그래도 구연자·채록지가 대량으로 정리돼 있어 인물·장소 전거 후보로 쓸 만함. 상세 요청 패턴은 `archives.md` 참고. 다음 세션에 스크립트로 받아서 프로젝트 키워드로 필터링해볼 만한 유력 후보
- **경기 여성 '나'를 말하다(data.gg.go.kr, 경기데이터드림)**: 신규 후보 3건 중 하나. 세대별 여성 생애 이야기를 담은 PDF 1건(2018년 경기도 여성비전센터 발간, 갱신 없음, 102MB·157쪽)짜리 자료. **판정: ✅, 단 조건부** — 화면상 "데이터 활용목적" 선택 모달을 거쳐야 할 것처럼 보이지만 실제로는 게이트가 아니라서 `GET /portal/data/file/downloadFileData.do?infId=...&infSeq=...&fileSeq=...`로 바로 받아짐. 다만 **기본 curl은 사이트 WAF에 막힘** — 일반 브라우저 User-Agent와 사전 방문으로 받은 쿠키를 같이 보내야 통과됨(둘 다 확인 완료). PDF라서 텍스트/이미지 여부에 따라 추가로 OCR이 필요할 수 있음 — 아직 파일 내용까지는 확인 안 함
- **무형유산지식백과 스페셜리스트(ichpedia.org/specialist)**: 신규 후보 3건 중 하나. **판정: ◐ — 스크래핑 자체는 쉽지만 "구술" 관련성은 낮음.** 로그인 불필요, `GET /specialist/list?page=N` + `/specialist/detail?id=N` 패턴의 평범한 서버 렌더링 HTML(전체 56건, 2026-07-26 기준). 그런데 실제로 열어보니 대부분은 사진작가 정진국이 2006년 찍은 생활사 사진 에세이(조선소·경마장·시장 등, 기록형태가 "이미지")고, "OO의 구술생애사"라는 제목이 붙은 항목도 몇 건 있지만 이 역시 사진 1장 + 짧은 캡션이지 음성이나 녹취 전문이 아님. 같은 사이트의 "수집자료" 탭(16,511건)도 확인해봤는데 판소리 등 무형문화재 보유자의 교육자료·상패 위주라 더 거리가 멂. 사료(사진) 출처로는 쓸 수 있어도 구술 자료로서의 실익은 낮아 보임 — 우선순위 낮음
- **대한민국 신문 아카이브(nl.go.kr)**: API 없음 확인. 기획 노트 3-5의 "LOD 제공"은 신문 아카이브가 아니라 국립중앙도서관 서지(도서) 데이터용 별도 서비스였음 — 문서 정정 필요. 검색 폼 자동 제출도 여러 방법(클릭/Enter/JS 함수 직접 호출)으로 시도했으나 실패
- **네이버 뉴스라이브러리**: 브라우저 정책상 도메인 자체가 차단되어 접근 불가

## 4. 기획 문서 대비 달라지거나 새로 생긴 부분

문서에 없던 결정들이라 여기 남겨둡니다 (나중에 기획 정리노트에도 반영할지 검토 필요):

- **`links` 테이블의 실제 활용 예시**: 연표 화면에서 "직접 연결/간접 연관/무관" 3단계 시각화로 구체화함 (색은 이번에 호박·회색 계열 → 주황·파랑·회색으로 변경)
- **각주(notes)라는 새 개념**: 원본 구술 자료에 이미 달려 있던 각주(엑셀이 각주를 못 담아 별도 컬럼으로 분리된 것)를, "이견"(자료 간 사실 충돌)과 구분되는 별개 필드(`SegmentCardData.notes`)로 다룸. 이견은 판단하지 않고 병기하는 것, 각주는 채록·편집 과정의 보충 설명·정정이라는 점에서 성격이 다름
- **출처(sources_authority) 링크 처리**: 구술 목록에는 매번 링크(짧은 라벨), 연표의 국사편찬위원회 출처는 라벨은 짧게 유지하되 호버 시 정식 명칭, 클릭 시 원본 페이지로 — "타이틀은 살리되 줄은 안 늘어나게" 하는 절충
- **`ArchiveItemType`에 "문서" 신설**: 신문(기사)과 정부 기록물(문서)을 아이콘·색으로 구분(🗂️, stone 계열). 국가기록원에서 가져온 진짜 기록물 5건을 신문 → 문서로 재분류함
- **6-5(API 연동 및 저장 방식) 정정**: 원래 "원문까지 저장"이 모든 API에 일괄 적용되는 것처럼 쓰여 있었는데, 한국민족문화대백과사전 신청서를 쓰다가 이게 저작권 있는 2차 저작물(백과사전)에는 안 맞는다는 게 드러나서, **출처 유형별로 저장 범위가 다르다**로 고침 (1차 사료=원문 저장, 백과사전류=요약·링크만)
- **장소 전거에 좌표 추가**: 기획 문서 6-1-1엔 인물 전거(`person_authority_id`) 부재만 지적돼 있었는데, 장소 쪽도 좌표(`PlaceRef.lat/lng`)가 없으면 지도 연결이 안 된다는 게 드러남 — 인물 전거와 마찬가지로 스키마에 반영 필요
- **연표 표시 밀도(SCALE) 개념**: 100년 스케일을 다루기로 하면서 필요해진 완전히 새로운 기능

# 2부 · 화면을 왜 그 꼴로 세웠나 (2026-08)

> 1부(위)는 초기 구현 시점의 스냅샷이고, 여기부터는 **README에서 내려온 판단 근거**다.
> README는 "무엇이 어디 있나"만 지고, "왜 그렇게 했나"는 이 절이 진다(2026-08-29에 갈랐다).

## 구술 사업 — 왜 카드가 아니라 상자인가

사료는 손에 잡히는 낱장 하나(**건**)지만, 구술 사업은 한 사업이 낳은 한 벌(**계열**)이다. 기록학의
다층기술은 `계열 → 철 → 건`으로 층을 나누고 층마다 서식을 달리 두는데, 사료 카드(`RecordCard`)와
같은 크기·같은 테두리로 격자에 늘어놓으니 담는 것과 담기는 것이 같은 급으로 서 있었다.

**라벨은 ISAD(G) 2판의 국제 교환용 필수 6요소만 진다** — 참조코드·기술계층·생산자·제목·일자·규모.
나머지 스무 요소는 열었을 때 나온다(다층기술 규칙 4.1 "계층에 적합한 정보"). 확인 수준(`●●●`)은
영역으로는 기술통제(3.7)지만 라벨 맨 위 오른쪽에 둔다 — 이 상자를 열어 볼지 말지를 가르는 첫
잣대라 훑는 눈에 먼저 걸려야 하기 때문이다.

### 말은 두 벌로 쓴다 — 규칙어와 카테고리

층위는 규칙어 그대로다: ISAD(G) 2판의 fonds → series → file → item을 국가기록원 기술 규칙의
우리말로 옮긴 **기록물군 → 계열 → 철 → 건**이고, 사업 하나가 곧 **계열**이다. 반면 선반을 가르는
**1~6·A는 층위가 아니라 분류**다 — 원칙대로면 1~6은 주제로 묶은 **주제군**이고 A는 주제가 아니라
**출처·행위자 축**이라, 둘을 한 번에 세는 규칙어가 애초에 없다. 그래서 묶음 쪽만 규칙어가 아닌
**카테고리**로 부른다(규칙 밖의 것에 규칙어를 갖다 쓰면 층위와 헷갈린다 — 기술 칸의 `L1`·`L2`와
같은 처리다). **층위는 규칙어로, 묶음은 카테고리로.**

### 라벨은 두 겹이다

| 겹 | 무엇 | 색 | 누를 수 있나 |
|---|---|---|---|
| 왼쪽 글리프 `● ◐ ╱ ·` | 문서에 무엇이 적혀 있나 (자동 파생) | 없음 (모양·진하기로만) | 아니오 |
| 오른쪽 노란 획 | 내가 **검토**한 칸 — "여기는 더 볼 일 없다" | 노랑 | 예 |

색을 오른쪽만 가지는 것은 이 저장소의 규칙 때문이다 — **색은 사람이 손댄 흔적이고, 자료가 스스로
말하는 것은 색을 갖지 않는다**([globals.css](../src/app/globals.css)).

네 상태 가운데 **`╱ 봤으나 못 찾음`과 `· 아직 안 봄`을 가르는 것이 핵심**이다. 앞은 기관이 공개하지
않는다는 *발견*이고(그 자체가 조사 결과다), 뒤는 아직 손대지 않은 다음 조사 대상이다. 둘을 한
칸으로 뭉개면 무엇을 더 조사해야 하는지가 사라진다. 문서가 채웠나(`확인`)와 내가 읽었나(`검토`)는
다른 층이라, 말도 갈라 둔다.

라벨은 칸 이름 대신 **군**을 세운다 — 서른 줄은 상자가 아니라 표가 되기 때문이다. 다만 군마다
칸 글리프를 한 줄로 눕혀 실어, 접힌 채로도 어느 칸이 비었는지는 그대로 보인다. 덧창의 난간도
군을 접었다 펴고, 대장은 한 번에 군 하나를 눕힌다.

### 칸의 빈자리가 곧 다음 조사 목록

56건은 2026-08-27에 전부 새 칸으로 옮겼다. 파서는 옛 육하원칙 꼴도 계속 받는데(새 항목을 옛 꼴로
적어도 화면이 안 죽도록), 지금 문서에 옛 꼴은 없다. 2026-08-28에 계열이 117건으로 늘어난 뒤 다시
세면 「권리 귀속」은 **117건 중 확인 0건**(안 봄 96 · 못 찾음 13 · 일부 8)이고, 「범위와 내용」은
**50건이 「일부」**(소재만 있고 시대·지역이 빔), 활용 「공개」는 **57건이 안 봄**이다. 계열이 갑절이
되는 동안 권리 귀속은 한 건도 안 찼다 — **기관이 밖에 안 내놓는 칸**이라는 뜻이다.

칸 구성 자체의 근거(기술 축 23칸 + 활용정책 축 9칸, 활용 군이 중심인 이유, 로컬 칸 `L1`·`L2`)는
[기술 칸 규격](oral_description_schema.md)이 진다.

### 수행기관을 서가에서 뺀 이유 (2026-08-28)

카테고리 A는 나머지와 축이 다르다 — 1~6번은 "이 기관이 이런 사업을 벌였다"는 주제 묶음이고, A는
"남의 사업을 대신 채록한 쪽"이라 출처·행위자 축이다. 같은 선반에 얹으면 상자 넷이 주제 하나인 것처럼
보인다. 상자가 아니라 **표**인 것도 그래서다 — 이쪽을 읽는 물음은 "이 사업이 무엇인가"가 아니라
**"누구 밑에서 몇 건을 했나"**여서, 넷을 나란히 눕혀야 답이 보인다. 하위구분(수탁형/과제형)과 수주
건수가 한 열로 서면 둘이 짝을 이루는 것이 그대로 드러난다 — **수탁형만 수주 건수가 있다.**

### 대장이 따로 있는 이유

서가는 하나를 고르는 자리라 상자마다 제 라벨을 들고 서 있고 같은 칸이 세로로 서지 않는다.
"누가 열람절차(3.4.1)를 확인했나"처럼 한 요소를 113건에 걸쳐 훑으려면 눕힌 표가 따로 있어야 한다.

### 둘을 쌓다가 탭으로 갈랐다 (2026-08-28)

본래는 갈아 끼우면 둘 중 하나가 늘 숨는다는 이유로 세로로 쌓았는데, 계열이 117건이 되자 카테고리

## 사건 없이 연표에 서는 사료

연표 한 행이 반드시 사건일 필요는 없다. 신문기사 한 건도 그 자체로 "언제 무슨 일이 있었나"를
증언하고, 붙일 사건이 아직 없다는 것은 그 기사에 연표에 설 값이 없다는 뜻이 아니라 사건 쪽
정리가 안 됐다는 뜻일 뿐이다. 그래서 사료가 사건을 거치지 않고 제 이름으로 한 행을 차지할 수 있다.

- **설 수 있는 것은 옮겨 적어 둔 본문이 있는 사료뿐이다**(지금은 신문기사 90건). 본문이 없으면
  내용 칸이 비어 날짜 하나만 놓인 빈 행이 된다 — 사진·유물은 사건에 붙어 그 행의 사료 칸에 설
  때 제 몫을 한다. 구술도 이 길로는 서지 않는다. 잣대는 [types.ts](../src/lib/types.ts)의
  `hasTimelineBody` 한 곳에 두고 화면(보류함 버튼)·서버(올리기 액션)·질의가 함께 쓴다.
- **올리는 것은 사람이 정한다.** 날짜가 있다고 저절로 올라가지 않는다 — 보류함(`/admin/review`)
  에서 골라 `연표에 올리기`를 눌러야 `adopted_at` 딱지가 찍힌다.
- **연표에 설 날짜를 따로 받는다**(`timeline_date_value`, EDTF). 신문의 발행일은 기사가 실린
  날이지 그 일이 일어난 날이 아니다 — 1961-09-20자 「그저 한산하기만-추석대목 서울의 상가」가
  증언하는 것은 "앞으로 나흘이면 추석"인 9월 24일 무렵의 장바닥이고, 1983-08-05자 동대문시장
  기사는 78~79년의 형성 과정을 적고 있어 한 점이 아니라 구간(`1978~1983`)으로 서야 맞다.
  올릴 때 발행일로 채워만 두고, 연표에서 보며 조정한다(행 메뉴의 `날짜`). **발행일 자체는
  고치지 않는다** — 그것은 자료의 사실이고, 화면은 둘을 나란히 보여준다.
- **칸의 뜻을 지킨다.** 사료는 사료 칸에 서고 **사건명 칸은 비운다**. 자료 제목을 사건명 칸에
  채워 넣으면 표를 훑을 때 사건인지 자료인지 구별할 수 없게 되고, 비어 있다는 것 자체가 "아직
  사건으로 묶이지 않았다"는 읽을 만한 정보다. 내용 칸에는 원문을 통째로 싣는다. 사료·구술 칸을
  접어 두는 사건 관리 화면에서만 자료가 사건명 칸 자리에 서는데, 그때는 앞에 「사료」 딱지를 붙인다.
- **사건에 붙어도 이 행은 사라지지 않는다.** 올리는 것("이 자료는 그 자체로 연표에 설 값이 있다")과
  붙이는 것("이 사건과도 관계있다")은 별개의 판단이라, 하나가 다른 하나를 무르게 하지 않는다.
  대신 행에 "사건에도 붙어 있음 — 사건명"을 적어 두고, 거슬리면 행 메뉴의 `내리기`로 사람이
  내린다 — 붙였다고 기계가 조용히 치우지는 않는다.

## 편집 「사료」 (`/admin/review`) — 수집에서 연결까지 한 화면

외부 소스 검색은 **자료를 모으는 편집 작업**이라 사용자뷰가 아니라 편집 안에 둔다.

편집 탭 셋(`사건`·`사료`·`구술`)은 하는 일이 아니라 다루는 것으로 이름 지었다(2026-08-29) —
「편집」 화면 안이라 행위어가 없어도 뜻이 서고, 사용자뷰의 「구술 사업」과 글자가 겹치지 않는다. 화면은 왼쪽에
연결 대상 사건 목록을 계속 펼쳐두고(드롭다운을 쓰지 않아, 자료마다 목록을 다시 띄울 필요가 없음),
오른쪽 사료 카드에서 버튼 한 번으로 **저장과 연결을 동시에** 처리한다.

- 판단이 서지 않으면 `[보류]`로 자료만 저장. `links.status`의 `candidate`는 쓰지 않고, 나중에 자동
  매칭이 붙을 때 "기계가 제안한 연결"을 담을 자리로 비워둔다.
- 연결 후보 사건은 **같은 검색어로 걸린 DB 사건**이다. 보류함은 검색어가 없어 사건 전체가 후보라
  목록에 좁히기 칸이 붙는다.
- 사건을 지우면 사건과 연결선만 사라지고, 붙어 있던 사료·구술은 보류함으로 돌아간다.
- 국립중앙박물관 자료는 목록 API에 설명이 없어 유물마다 상세 API를 한 번 더 부른다(검색 1회당 API
  7회). 국가기록원은 상세 API가 없어 제목·생산기관·연도·열람 여부가 전부다.

## 연구 동향 — 수집 범위를 정한 근거

정본은 [scripts/fetch-riss-papers.mjs](../scripts/fetch-riss-papers.mjs)이고, 조건을 그렇게 잡은 이유는 이렇다.

- 학위논문은 "구술사"+"구술생애사" 정확검색 합집합(교육/종교/스포츠 계열 기관 제외).
- 학술논문은 "구술사"+"구술생애사"+"생애사" 정확검색 합집합 중 제목에 "구술"이나 "생애사"가 들어가고
  발행 지면이 인문·사회·복합학 계열인 것.
- 예술체육·의약학·공학·종교에 더해 **사회복지·특수교육·평생교육 지면도 받지 않는다**(2026-08-20) —
  생애사를 학습·전문성 연구의 *방법으로 빌려 쓴* 논문이 대량으로 섞여 들어오기 때문이다. 다만 제목에
  "구술"이 들어간 논문은 지면과 무관하게 받고(체육 제외), "학습생애사"가 들어간 논문은 받지 않는다.
- 『구술사연구』(한국구술사학회지)·한국구술사학회 학술대회 발행물은 조건과 무관하게 다 받는다.
- 화면에서 쳐낸 논문은 `npm run dump:cut`으로 [data/cut-papers.json](../data/cut-papers.json)에 등록번호가
  적히고 다음 수집 때 아예 다시 긁지 않는다. 되살리려면 그 줄을 지운다.

## 백업 일정을 따로 뗀 이유

- launchd `com.fragment-index.backup`이 매일 14:00에 돈다. 그 시각에 노트북이 잠들어 있으면 깨어날 때,
  꺼져 있으면 다음에 켤 때 한 번 돈다(며칠 건너뛰어도 몰아서 돌지 않는다). 등록 파일이 저장소 바깥이라
  맥을 새로 세팅하면 다시 만들어야 한다.
- **안 바뀐 날은 파일을 만들지 않는다** — 직전 스냅샷과 `counts`·`tables`가 같으면 건너뛴다(`savedAt`은
  돌린 시각이라 비교에서 제외).
- **7일 지난 스냅샷은 달마다 하나의 `YYYY-MM.tar.gz`로 묶는다**([rotate-backups.mjs](../scripts/lib/rotate-backups.mjs)).
  지우지는 않는다 — 실수를 알아차리는 것은 대개 며칠 뒤라 7일에서 잘라 버리면 정작 필요할 때 없고,
  JSON은 5~6배로 줄어 한 달치를 다 담아도 3MB 안팎이라 버려서 아낄 것이 없다.
- **에이전트를 따로 둔 이유**: 그전까지 백업이 독립된 일정 없이 주간 스크립트에 얹혀 있었다. 그쪽은
  RISS 수집이 본업이고 "6일 안 지났으면 건너뛰기" 가드가 걸려 있어, 가드에 걸리는 주에는 백업까지
  통째로 건너뛰었다(실제로 2026-08-24 08:00에 그랬다). 지금도 주간 스크립트는 동기화 직전 상태를
  남기려고 `backup`을 먼저 부르지만, 그것은 부산물이지 백업 일정이 아니다.
- 백업이 담는 것은 **사람의 판단만**이다 — 화면에서 손으로 만든 것(발췌·인물·사료·출처·인용·연결선)은
  통째로, 기계가 긁어온 `timeline_events`·`papers`는 그 위에 얹힌 것만(연표로 꺼낸 딱지, 저장·메모·강조,
  쳐낸 표시, 직접 만든 행). 6천여 건의 재고 본문은 스크립트를 다시 돌리면 되므로 담지 않는다.
  복원은 파일을 보고 사람이 판단해 넣는다 — 통째로 되밀면 스냅샷 이후에 한 일까지 되감긴다.

## PRISM 수집에서 걸린 것

- 이 API에는 **낱말 검색이 없다**(목록이 받는 조건은 기관코드와 연구기간뿐). 기간으로 전량을 훑고
  제목을 이쪽에서 거른다 — 개발계정 하루 1,000건 제한에 걸리기 쉬워 목록은

- 과제명만 같고 채록이 아닌 것(항공영어구술능력증명·구술심리제도)은 `import:prism`에서 걷어낸다.
